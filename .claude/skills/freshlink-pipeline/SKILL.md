# FreshLink 작업 파이프라인 (에이전트 하나, 순서대로)

**일하는 Claude는 하나다.** 지금 사용자와 대화하는 메인 세션(Opus 5.5)이 처음부터 끝까지 직접 이해하고, 고치고, 검증한다. 일을 다른 에이전트에게 넘기고 결과를 기다리는 방식(위임형)은 쓰지 않는다. 파일 보고서(`_workspace/`)도 만들지 않는다. 메모가 필요하면 대화 안에 짧게 적는다.

> 2026-11-13 변경: 예전에는 PM(메인 세션)이 서브에이전트 7개(planner, architect, coder 3종, verifier, reviewer)에게 차례로 일을 넘겼다. 넘길 때마다 맥락을 다시 읽고 파일로 주고받느라 쉬운 요청도 오래 걸려서 이 방식으로 바꿨다.

## 0단계. 크기 정하기 (먼저, 10초 안에)

요청을 읽고 아래 셋 중 하나로 정한 뒤 사용자에게 한 줄로 알린다. 예: "작은 일로 보고 바로 고칠게요."

| 크기 | 예 | 거치는 단계 | 사용자 확인 |
| --- | --- | --- | --- |
| **작은 일** | 값 하나, 오타, 문서 몇 줄, 질문 답, 로그 한 줄 읽기 | 1 이해(짧게) → 3 구현 → 4 빠른 검증 | 커밋·PR 전에만 |
| **보통 일** | 한 레포 안의 API 하나, 화면 하나, 모듈 하나, 버그 하나 | 1 → 2 계획(5줄) → 3 → 4 → 5 자체 리뷰 | 계획 뒤 1번 + 커밋·PR 전 |
| **큰 일** | 레포 여러 개, 쪽지 형식 변경, 새 서비스, prod·비용에 영향 | 전 단계 | 계획 뒤 1번 + 커밋·PR 전 |

- 애매하면 한 단계 작은 쪽을 고른다. 진행하다 커지면 그때 올린다("생각보다 커서 계획부터 보여 드릴게요").
- 질문·설명만 원하면 파이프라인을 쓰지 않고 바로 답한다.
- 리뷰만 원하면("이 PR 리뷰해줘") 5단계만 한다.
- 사용자가 "끝까지 쭉", "알아서 해"라고 하면 계획 확인도 건너뛴다. **커밋·PR 전 확인과 아래 절대 규칙은 그래도 지킨다.**

## 1단계. 이해

- 작업할 레포의 `CLAUDE.md`를 먼저 읽는다. 레포 규칙이 이 문서보다 우선이다.
- 영역별 사실과 점검표는 필요할 때만 연다. 고치는 레포에 해당하는 파일 하나만 읽는다.
  - 백엔드(gateway, *-service, logistics-simulator, common): [backend.md](backend.md)
  - 인프라(infra, gitops, 워크플로): [infra.md](infra.md)
  - 프론트(frontend): [frontend.md](frontend.md)
  - `.github` 문서만 고치면 아무것도 열지 않는다.
- 관련 코드는 필요한 파일만 찾아 읽는다(Grep·Glob 먼저, 통째로 읽기는 나중). 레포 전체를 훑지 않는다.
- 기준 문서는 `.github` 레포 `docs/`(목차 `docs/README.md`)다. 필요할 때 그 문서만 연다.

## 2단계. 계획 (보통·큰 일)

5~10줄로 쓴다. 파일로 저장하지 않는다.

```
### 계획 — 이대로 진행할까요?
- 바꿀 곳: inventory-service(폐기 API), gateway(라우트)
- API·쪽지·테이블: POST /api/owner/disposals (OWNER), 쪽지 형식 변경 없음
- 검증: ./gradlew build, 폐기 수량 음수 테스트
- 다른 담당자·인프라 할 일: gateway 라우트는 내가 고침 / gitops 환경 변수 없음
- 정해 주세요: (미확정 질문. 없으면 "없음")
```

- 수용 기준은 확인할 수 있는 문장으로 쓴다("유통기한 지난 lot은 예약되지 않는다").
- 아래 "꼭 묻는 것"에 해당하면 여기에 함께 적는다.
- 사용자가 ok 하면 3단계로 간다. 고칠 점을 말하면 계획만 고쳐 다시 보여 준다.

## 3단계. 구현

- 직접 고친다. 여러 레포면 순서를 지킨다: 백엔드는 common → 서비스 → gateway, 인프라는 infra → gitops → 서비스 레포 CI 호출부.
- 레포는 한 폴더 아래 나란히 있다(예: `C:\fresh-link\repos\*`). 세션을 연 레포 밖도 같은 세션에서 고친다.
- 설계와 달라지면 그 자리에서 사용자에게 한 줄로 알리고 계속한다(묻는 것이 아니다).
- 테스트가 필요한 변경이면 테스트도 같이 쓴다.

## 4단계. 검증 (빠지면 안 된다)

- **바뀐 레포만** 검증한다. 명령은 영역 파일(backend.md·infra.md·frontend.md)의 "검증" 표를 따른다.
- 작은 일: 바뀐 레포의 빌드 또는 lint 하나 + 비밀값 검색. 문서만 고쳤으면 링크·표 모양만 본다.
- 실패하면 원인을 고치고 **실패한 것부터** 다시 돌린다. 같은 실패가 3번 넘게 안 풀리면 멈추고 상황과 선택지를 사용자에게 묻는다.
- 도구가 없으면 설치하지 않고 "미실행(도구 없음)"으로 적는다. 돌리지 않은 검증을 통과했다고 말하지 않는다.
- 테스트를 지우거나 `@Disabled`·`skip`으로 통과시키지 않는다.

## 5단계. 자체 리뷰 (보통·큰 일, 리뷰 요청)

- `git diff`를 처음부터 끝까지 다시 읽고 영역 파일의 "리뷰 점검표"를 위에서부터 확인한다.
- 문제는 `path:line — 문제 — 수정안`으로 적고, 내 변경이면 바로 고친 뒤 4단계 검증을 다시 돌린다.
- 남의 PR을 리뷰할 때는 `gh pr diff <번호>`로 읽고 코드를 고치지 않는다. PR에 댓글은 사용자가 원할 때만 단다.
- README API 표·데이터 모델·values 키처럼 문서가 따라가야 하는 변경이면 이 단계에서 문서도 고친다.

## 6단계. 커밋·PR (사용자 ok 뒤에만)

확인 메시지에 레포별 브랜치 이름, 커밋 메시지, PR 대상 브랜치, 라벨을 미리 적는다.

```
### 커밋·PR 올릴까요?
- inventory-service: feat/S-32-dispose → dev, "feat: 유통기한 지난 lot 폐기 API"
- 검증: ./gradlew build 통과, 비밀값 없음
- 리뷰: 지적 1개 고침 (소유권 확인 누락)
```

- 작업 브랜치 → 커밋 → `git push -u origin <브랜치>` → `gh pr create`. 서비스 레포·frontend는 `dev`, `infra`·`.github`·`gitops`는 `main`. 레포 `CLAUDE.md`·`.github` `CONTRIBUTING.md`가 다르면 그것을 따른다.
- 커밋·PR 제목: `feat:`/`fix:`/`docs:`/`chore:` + 한국어 요약. PR 본문은 공통 PR 템플릿을 채운다.
- 합치기는 사람이 CI 통과를 보고 한다. `gh`가 없으면 push까지만 하고 PR 만드는 링크를 준다.

### 마지막 보고 (3~6줄)

- PR 링크(합치는 순서대로), 검증 결과, 사람이 할 일(PR 합치기, `terraform apply`, 다른 담당자에게 알릴 것, 프론트 영향).

## 서브에이전트·병렬 작업을 쓰는 경우 (예외)

기본은 혼자 순서대로 한다. 아래일 때만 Agent 도구로 서브에이전트를 **잠깐** 띄운다. 띄우기 전에 이유를 한 줄로 알린다.

| 쓰는 경우 | 방법 |
| --- | --- |
| 레포 여러 개를 동시에 **읽기만** 해서 찾아야 할 때 (예: 6개 레포에서 쪽지 type 사용처 찾기) | 레포마다 읽기 전용 탐색 하나씩 병렬로 띄우고 결론만 받는다 |
| 큰 일에서 내 판단에 묶이지 않은 리뷰가 필요할 때 | 5단계 뒤 리뷰 하나만 띄운다. 내 결론 말고 diff와 점검표 경로만 넘긴다 |
| 오래 걸리는 명령(전체 빌드 여러 개)을 기다리는 동안 다른 일을 할 수 있을 때 | 백그라운드 실행 |

- 서브에이전트끼리 일을 주고받게 하지 않는다. 결과는 항상 메인 세션이 받아서 판단한다.
- 코드를 고치는 일은 맡기지 않는다. 고치는 것은 메인 세션이 한다.

## 절대 규칙

```
⛔ main·dev 직접 push, git push --force, git reset --hard, git clean, 브랜치 삭제, 히스토리 재작성 금지
⛔ 커밋·push·PR은 사용자가 ok 한 뒤에만
⛔ terraform apply / destroy / import / state 변경, kubectl apply·delete·edit, helm install·upgrade 금지 (사람이 한다)
⛔ aws CLI로 리소스 생성·수정·삭제 금지 (Cognito 사용자·그룹 포함). 읽기도 사용자 확인 후
⛔ DB DROP / TRUNCATE / 조건 없는 DELETE, 큐 purge 금지. prod DB는 읽기도 사용자 확인 후
⛔ 비밀값(DB 비밀번호, 토스 키, AWS 키, 토큰 원문, tfvars 실값, kubeconfig, state)을 커밋·출력하지 않는다
⛔ 도구 권한이 거부되면 다른 방법으로 우회하지 않고 사용자에게 알린다
```

## 꼭 사용자에게 묻는 것

- 커밋·push·PR (6단계)
- 계획의 미확정 질문 (팀이 아직 정하지 않은 것을 지어내지 않는다)
- 담당자가 다른 레포(CODEOWNERS가 사용자가 아닌 레포)를 고칠 때 — 담당자 이름과 함께
- 쪽지(SQS 메시지) 형식 변경 — `message-spec` 라벨, 이태우·김경우 알림 필요
- 비용이 늘어나는 인프라 변경 — 월 비용 영향과 함께
- `terraform plan`처럼 실제 AWS 계정을 읽는 명령

## 말투

- 사용자에게 하는 말과 레포에 커밋되는 것(README, docs/, 코드 주석, PR 본문)은 평이한 한국어 문장(`~한다` 체).
- 진행 중 알림은 한 줄. "대기 중", "추가 지시 있으면" 같은 끝인사는 쓰지 않는다.
